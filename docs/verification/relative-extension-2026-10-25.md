# 跨消息相对延期核对

## 实现行为

支持独立、肯定的延期指令，例如“上次报告再延三天”“实验一延期3天”“第一次作业顺延两天”。可识别数字及常见中文数字，按天、周、小时或分钟计算；计算基准是已确认原任务的截止，不使用接收、扫描或识别任务的时间。

计算在服务端创建草稿的事务内完成。课程和班级严格匹配；明确名称使用准确名称匹配，“上次报告”等泛指仅在范围内恰好一个符合条件的未完成任务时匹配。不会选择最近任务，也不会用相似度替代确认。无课程、多个可能任务、原截止未知、通知发布时间未知或通知顺序不明时，只留下待核对草稿。

纯日期按天/周延期仍保留纯日期，不补 23:59；小时和分钟延期需要原截止有明确时刻。原文明示了完整的新截止日期时，仍可使用原文明示日期，供用户核对。

学习通课程通知按通知正文识别，并保留原标题及正文原文。未获取发布时间时保留核对入口，不使用扫描时间推算。含额外条件、附加复杂正文或未核对附件时不自动推断；未解析的相对延期不会被当作新任务确认。多任务通知使用确定的任务段落，避免把无关的新任务也改成延期。

## 确认、重复和证据

- 草稿显示“原截止＋延期量→建议新截止”，多个可能原任务可打开查看；确认后才更新原任务。
- 保存原任务编号、原版本、原截止、原截止来源编号、延期量、通知发布时间及原文表达。原任务变化后，旧草稿不能直接确认，需刷新核对。
- 同一任务、同一发布时间、相同延期量按同一核对事件处理，包括跨来源重新表述。已确认的延期重新导入或重新提取时只关联来源，不再次累加。确有新的连续延期，需要新的、明确较晚的通知发布时间；相同发布时间无法区分先后的多次延期需人工核对。
- 新通知可继续在已确认的新截止基础上延期；不同通知的待确认草稿分别保存，不提前合并成累加结果。
- 延期通知发布时间属于变更来源，不替代原任务首次发布时间；原任务发布时间未知仍显示未获取。检查清单、提交方式及原始来源保留。
- 混合模式的明确相对延期交给服务端计算，避免 Qwen 用当前日期猜测；评测轨迹单列 relative_extension，不计为已调用模型。旧单通知评测使用隔离空任务库，不能据此验证跨消息解析效果；此功能用独立任务序列测试验收。

## 验证

相对延期用例覆盖唯一/歧义匹配、课程与班级范围、日期精度、未知原截止/发布时间、版本变化、重复导入和重新提取、连续延期、不同待确认消息、多任务通知、明确新截止及首次发布时间保留。另补充验证了不同的歧义延期草稿不会被合并。

最终全量 Python 测试 497 项、桌面端 48 项通过。新增浏览器流程验证计算展示、人工确认、重复幂等、歧义候选及 390px 布局；原截止变更、分歧核验及评测界面流程通过。

激活时原本的 8765 服务已停止，原重启脚本在第一步只读状态检查时退出，未修改业务数据。随后使用离线备份启动入口，备份至 data/backups/before-relative-extension-offline-20261025-112000；启动后五张业务表哈希一致，189 条消息、16 条任务、60 条草稿、28 条来源关联和 67 条历史记录均保留。在线脚本已提供计算和候选核对展示。96 条标注文件仍为原哈希，人工核对数仍为 0。

证据位于 artifacts/relative-extension-20261025/，包含 regression.log、task-time-ui.log、hybrid-ui.log、evaluation-ui.log、deployment.json；新增浏览器入口 scripts/test-relative-extension-ui.cjs。测试在临时数据库执行，未创建真实业务任务。新的真实留出样本尚未人工核对，不宣称总体准确率提升。
