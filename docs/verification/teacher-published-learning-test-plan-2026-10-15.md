# 学习通测试课真实发布验收方案（2026-10-15）

目标：用一门仅包含测试账号的学习通课程，验证发布账号操作 → 学生端可见 → CourseInbox 采集原文 → 提出任务草稿/变更 → 人工确认的真实链路。发布账号可以先试用现有个人账号建课；是否具备入口以实际界面为准，不以学校教师认证为测试前提。发布与学生提交都由用户在学习通官方界面手动完成；CourseInbox 只读采集，不代发通知、作业或提交答案。

## 准备

1. 先用现有学习通账号检查“课程/我的课程 → ＋ → 新建课程”是否可用；若可用，就建立名称明显标注“测试”的课程和班级，只让单独的学生测试账号加入。发布与接收应使用不同账号；记录课程名、班级名，但不要把密码、验证码、手机号写入仓库。
2. 学生账号登录 CourseInbox 的学习通同步端；启动电脑服务并核对聊天、课程通知、作业/考试三个来源各自的状态。手机使用 0.3.14，通知使用权与应用通知权限分别核对。先记录版本、北京时间和测试前的消息/任务数。
3. 每发布一条，先确认学生学习通页面实际可见，再检查 CourseInbox。等待来源完成一轮检查；`partial`、`retrying`、有待处理数时继续记录状态，不能直接判为无消息。

## 按顺序发布和检查

| 编号 | 教师端动作 | CourseInbox 应检查的结果 |
| --- | --- | --- |
| T1 | 发课程通知：`【CI-TEST-01】数据库实验三，请在{明确日期时间}前通过学习通提交 PDF。` | 课程通知原文、来源、发布时间入库；提出 CREATE 草稿，字段有原文依据；确认前不进入正式任务。 |
| T2 | 在测试班级聊天发另一项明确任务，使用不同标题。 | 聊天来源独立入库；课程/班级归属正确；不与 T1 错误合并。 |
| T3 | 在“作业”真正发布 `【CI-TEST-03】实验报告`，设置明确截止、提交方式，并放一个无个人信息的 DOCX/PDF 附件。 | 作业中心来源保留平台链接与稳定身份；可见字段、附件名称/链接有据可查；读不到的详情标为待核对，不猜测内容。 |
| T4 | 若平台允许，修改 T3 已发布作业的截止；另发通知：`【CI-TEST-03】实验报告截止改为{新日期时间}，其他要求不变。` | 保留前后两份来源；提出 UPDATE 原任务，需用户确认；确认后截止改变且历史可追溯，不凭缺失日期更新。 |
| T5 | 重发 T4 相同文字，再发一条与现有截止相矛盾的明确通知。 | 重复消息不产生重复正式任务；冲突进入 CONFLICT/人工核对，旧任务不被静默覆盖。 |
| T6 | 发非任务通知：`【CI-TEST-06】今天只通知教室变更，没有新作业。` | 原文可查，但不应产生作业草稿。 |
| T7 | 发仅含图片或附件要求的通知；另把图片保存后通过手机“收件箱 → 全部消息 → 识别图片”手动导入。 | 自动采集不凭图片文件名编造正文；手动 OCR 结果可校对、原图可查看，任务仍须确认。 |
| T8 | 学生账号对 T3 手动提交无个人信息的测试文件；如可用，教师再执行退回。 | 平台“已交/退回”作为观察值显示；本地任务状态仅在用户确认采用后改变。 |
| T9 | 在学生手机后台/锁屏时再发布一条通知，检查学习通是否真的产生 Android 系统通知。 | 若系统通知存在，CourseInbox 才能测试手机通知接收；记录实际通知文字，摘要不能算成完整正文。若平台未发系统通知，此项标记“平台无推送”，不要归因为监听失败。 |

每项分别记录：教师操作时间、学生端看到的页面/通知、CourseInbox 来源状态、原文是否完整、草稿操作类型与字段、是否人工确认、实际结果、失败截图。截图须遮盖个人信息。T1–T9 是可控端到端用例，不能直接当作 PPT 中 100–200 条真实通知测试集或 ≥90% 识别率的证明；后者需要另建标注集并统计任务识别、截止提取、更新判断及耗时。

参考：[学习通教师使用指南](https://special.chaoxing.com/mobile/mooc/tocourse/98551464)中的注册登录、建课建班、公告通知和作业章节。平台界面或教师权限以实际账号为准。
