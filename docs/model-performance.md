# 本地模型速度

针对本机 i5-12500H / RTX 3050 Laptop 4 GB 的处理延迟，项目的 Ollama 请求已调整为：

- `keep_alive: "5m"`：请求后保留模型五分钟，连续处理通知时复用已加载模型。空闲超时后仍会释放资源。
- 保留 `num_thread: 2`。曾尝试自动线程选择，但未验证到稳定收益，已恢复原限制，避免两套服务因运行参数不同而反复切换模型实例。
- 保持关闭思考模式、规则优先、原文核验和人工审核，不通过截断通知或直接确认任务来提速。

重启项目服务后才会使用新参数。其他仍发送 `keep_alive: 0` 的旧服务可能继续要求卸载模型，连续测速前应停止旧项目实例。首次加载和超过驻留时间后的首次调用仍可能较慢。

后续已查实原项目 8765 与融合版 8877 同时启用了学习通同步，且在 20:13–20:16 间出现重叠模型请求。融合版这条 96609 ms 的记录包含两次请求：加载阶段分别 47954 / 19540 ms，生成阶段分别 9097 / 17503 ms；第一次工具参数校验失败后进行第二次请求。加载耗时可能包含服务端调度等待，不能把两套服务竞争下的总耗时简单归因于线程数。应先停止一套后台，再对同一通知做对照测试；不自动停止用户原项目的后台同步。

用户随后授权暂停原项目：8765 已通过应用自身的暂停接口停止采集，队列与数据保留，8877 继续运行。用同一条合成通知及恢复双线程的隔离测试客户端连续测得 26719 / 56360 ms，两轮均为两次成功请求且无规则回退，仍存在明显波动。测试时融合版服务进程尚未重启加载线程回退，因此这些结果不能作为统一参数后的稳定性能结论。自动重启进程被审批策略拒绝，需手动重启融合版后再验证。

用户手动重启后已核对 8877 更换为新进程、8765 保持暂停。相同合成通知连续测得 45250 / 32641 ms，两轮均成功且无规则回退；四次请求的加载耗时分别为 8 / 6 / 6 / 8 ms。两轮生成耗时合计分别约 16.9 / 17.5 秒，说明模型驻留生效，但总耗时仍包含显著的调度等未细分开销，不能承诺已经达到秒级或稳定提速。融合版同步待处理队列当时仍有 16 项，测试不等同于完全空闲环境的单请求性能。

## 减少无效调用

继续排查确认两项问题，已修正：

- 任务中心重复采集可能更换网页消息编号。进入模型分析前，现在按既有 `capture_key` 查询同一平台任务的相同内容版本；相同版本及已清理版本直接交给既有去重 / 观察更新路径，不再次调用模型。正文、附件、截止或状态等版本内容真实变化时仍重新核对。没有扩大标题相似性缓存。
- 真实合成测速的第一轮工具调用失败原因为“提交方式原文依据缺少对应提交方式”。当模型没有填写提交方式，却给出了多余的引用时，现在只丢弃该引用，不接受或推断任何渠道，避免为这个无效字段再请求一次模型。实际填写的提交渠道、截止、任务操作和原文依据校验不变。

687 项后端测试通过，覆盖新增的版本复用、真实内容变化仍需分析、已清理版本不重复请求，以及无对应提交方式的引用不会触发第二轮模型调用。隔离客户端的同一合成通知首轮 13297 ms、一次成功请求、无规则回退；第二轮仍在 60016 ms 超时并保留规则结果。因此只确认调用次数减少，不能据此宣称稳定延迟改善。运行中的融合版尚需重启加载此次去重与校验修正，再观察实际后台负载下的表现。

Ollama 回执中新增数字型性能计数，保存在模型调用记录：`load_ms`、`prompt_eval_ms`、`generation_ms`、`input_tokens`、`output_tokens`、`tokens_per_second`、`total_ms`。已有 `elapsed_ms` 继续表示客户端实际请求耗时。计数不包含提示词、模型正文或凭据。

本次机器检查显示模型约 34% / 66% 在 CPU / GPU 上运行，显存总量 4096 MiB；检查时空闲约 306 MiB。可先关闭不需要的显存占用程序再测。减少上下文或更换更小模型需要另行验证提取效果，本次未自动更换模型或压缩上下文。

验证：684 项后端测试通过。合成通知连续测试存在 60 秒超时；其中一次成功请求的模型回执为总计 57.4 秒、加载 49.7 秒、输入处理 1.1 秒、生成 6.6 秒（147 tokens，22.22 tokens/s）。整轮包含后续失败请求，不能算作一次完整成功的提速对比；也不能与用户原通知的 29 秒直接比较。需要重启项目、避免旧请求干扰后，用同一条原通知对照测量。
